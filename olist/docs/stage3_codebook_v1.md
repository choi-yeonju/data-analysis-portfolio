# 코드북 v1 (3단계 수동 라벨 기준, 2026-10-21 확정)

- 근거 범위: dev `label_order` 1~50의 v0 라벨. hold-out은 보지 않았다. 리뷰 원문은 적지 않고 `label_order` 번호만 적는다.
- 위치: 규칙 문서 `stage3_step0_rules.md`(2488274로 동결)의 §3 코드북 v0를 이 문서가 대체한다. 동결된 본문은 고치지 않는다. 결정 기록은 `decisions.md` D-29.
- 출처 표시: **[메모]** 연주 님이 남긴 메모, **[라벨 점검]** 연주 님의 v0 라벨끼리 어긋나거나 갈린 지점(Claude가 찾음), **[제안]** Claude가 제안하고 연주 님이 채택한 경계. 확정(2026-10-21)은 연주 님이 했다.
- 이 문서는 첫 50건에서 나온 경계만 다룬다. 51번 이후에서 새 경계가 나오면 v2로 올리고 사유를 log에 적는다.

## 1. 유형 정의
| 코드 | 유형 |
|---|---|
| P1 | 상품 품질·불량·파손 (포장 불량으로 인한 파손 포함) |
| P2 | 설명·사진·사양과 다름 |
| P3 | 오배송(주문한 것과 다른 상품)·구성품 누락·일부만 도착 |
| P4 | 판매자·응대·환불·교환 |
| P5 | 가격·기대 불일치 |
| P6a | 배송이 늦었다·오래 걸린다고 언급 (late=0인데 지연을 언급) |
| P6b | 도착 기록이 있는데 아직 못 받았다고 하거나(안 왔다, 기다리는 중) 도착 여부를 묻는다 (**v0의 "미도착 주장"에서 넓어짐, 규칙 2**) |
| P9a | 기타 — 판독 불가: 번역과 원문으로도 불만의 이유를 알 수 없다 |
| P9b | 기타 — 체계 밖: 불만은 분명하나 P1~P6b 어디에도 안 맞는다 |

- 분석에서 P9a와 P9b는 둘 다 **P9**로 합쳐서 kappa·비중을 계산하고, 서브태그별 건수는 따로 적는다.
- P6b는 작성 시점(`answered_before_delivery`)을 확인하기 전에는 "고객 미수령"으로 단정하지 않는다. 결과 보고에서 P6b를 도착 전 응답과 도착 후 응답으로 나눠 함께 적는다(매핑 파일은 라벨링이 끝난 뒤에 연다).

## 3. 배송비 태그 `mentions_freight_cost` (v0 유지)
- True: 배송비(`frete`)의 금액·부담·청구를 언급한다(예: 배송비가 비싸다, 따로 냈다, 배송비를 받았다).
- False: 배송비 언급이 없거나 배송 속도·상태만 말한다(`frete`가 "배송"의 뜻으로 쓰인 경우 포함).
- U: 번역만으로 애매하고 원문의 `frete`와 금액·부담 단어를 확인해도 정해지지 않는다.
- 판단 순서: 번역 → 애매하면 원문 → 그래도 안 되면 U. (첫 50건에서 True는 #49 한 건)

## 4. 번역 주의 (v0 유지)
- 가려진 판매자 이름(`lannister`, `stark`, `targaryen`, `baratheon` 등)이 나오면 원문 기준으로 읽는다(번역이 상품·사람으로 오해하는 경우가 있다).
- `regular`는 번역이 아니라 원문 뜻(보통·그저 그렇다)으로 읽는다.
- 번역이 애매하면 원문을 확인하고, 원문으로도 판단이 안 되면 P9a.

## 5. 재라벨 절차
1. 이 문서와 D-29를 커밋·push한다.
2. `python tools\label_dev.py --pass relabel --ver v1`로 dev 1~50을 재라벨한다. 이 재라벨이 공식 라벨이다(§4 확정 규칙). 첫 라벨(v0)은 화면에 보이지 않는다.
3. 이 문서만 보고 판단한다. 첫 라벨과 일치율은 참고용이고 통과 판정에 쓰지 않는다. 자기 일관성(kappa)은 dev 51~100을 3~4일 간격으로 두 번 달아서 잰다.
4. 소요 시간(첫 라벨 v0, 재라벨 v1)은 따로 기록되고 `--summary`로 본다.
